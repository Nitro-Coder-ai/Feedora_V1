## Diff 1 — Schema ↔ Backend

**[OK] Pins columns.** `listPins` SELECTs `p.PIN_ID, p.MESSAGE_ID, p.CONV_KEY,
p.SCOPE_TYPE, p.PINNED_BY, p.PINNED_AT` (MessageRepository.php:103) — every column
exists in `MESSAGE_PINS` (migration:19–32). `pinMessage` INSERTs `MESSAGE_ID,
CONV_KEY, SCOPE_TYPE, GROUP_ID, PINNED_BY, PINNED_AT` — all present; `ON DUPLICATE
KEY` rides `uq_pin_message(MESSAGE_ID)` (migration:27) → idempotent re-pin works.

**[OK] Pins join columns.** listPins joins `m.SENDER_ID, m.CONTENT, m.IMAGE_URL,
m.SENT_AT, m.EDITED_AT, m.IS_DELETED` + `u.NAME, u.PROFILE_IMAGE`. `EDITED_AT` and
`IS_DELETED` are guard-added (migration:86–97); rest are pre-existing MESSAGES cols.

**[OK] Typing columns.** `setTyping` INSERTs `USER_ID, CONV_KEY, UPDATED_AT` with
`ON DUPLICATE KEY UPDATE` on PK `(USER_ID, CONV_KEY)` (migration:44). `getTyping`
reads `t.USER_ID, u.NAME, u.PROFILE_IMAGE` and filters `UPDATED_AT > DATE_SUB(NOW(),
INTERVAL ? SECOND)` — `UPDATED_AT` exists with `ON UPDATE CURRENT_TIMESTAMP`
heartbeat (migration:43). Default window 6s matches schema §3.

**[OK] Seen.** `getReadState` reads `MAX(MESSAGE_ID) … WHERE SENDER_ID=? AND
RECEIVER_ID=? AND IS_READ=1`. `IS_READ` is guard-added (migration:79–83); covered by
`idx_messages_seen(SENDER_ID, RECEIVER_ID, IS_READ, MESSAGE_ID)` (migration:103).

**[OK] Edit/Delete.** `editMessage` writes `CONTENT, EDITED_AT`; `softDeleteMessage`
writes `IS_DELETED` + deletes from `MESSAGE_PINS` in one transaction. All columns
present; both scoped `SENDER_ID = ?` in SQL (author-only at the data layer).

**[OK] Search columns.** `searchMessages` SELECTs `m.MESSAGE_ID, m.SENDER_ID,
m.RECEIVER_ID, m.GROUP_ID, m.CONTENT, m.IMAGE_URL, m.SENT_AT` + `u.NAME, u.PROFILE_IMAGE`
and subqueries `CHAT_GROUP_MEMBERS`. `GROUP_ID` guard-added (migration:63–69),
`RECEIVER_ID` made nullable (migration:72–76). Query matches schema §3 exactly.

**[OK] Repo signatures.** Every method chat.php calls exists with the schema §3
signature: `pinMessage(id,by,key,scope,?gid)` (chat.php:925), `unpinMessage(id,key)`
(:931), `listPins(key)` (:914), `editMessage(id,me,content)` (:954),
`softDeleteMessage(id,me)` (:972), `setTyping(me,key)` (:1000), `clearTyping(sender,key)`
(:401), `getTyping(key,me)` (:643,:662), `getReadState(me,active)` (:663),
`searchMessages(me,q)` (:1015).

**[OK] CONV_KEY built via repo helpers, never from request.** All four scope-bearing
actions derive the key server-side: `groupConvKey($gid)` / `dmConvKey($me,$peer)`
(chat.php:902,905,995,997; send_message:399–400; poll:643,661). No `$_POST['conv_key']`
read anywhere. A forged CONV_KEY in the body is ignored. Verified by grep.

**[OK] poll.seen.** Backend sets `$response['seen']` = int (chat.php:618 default 0;

1511,1515,1518) — all present in the repo SELECT. `MESSAGE_ID` String()-coerced,

**[OK] pin/unpin → pinned.** Backend sets `pinned` (chat.php:929,935). Frontend reads

**[OK] edit_message → edited/content.** Backend sets `edited` + (on success) `content`

**[OK] delete_message → deleted.** Backend sets `deleted` (chat.php:976). Frontend

**[OK] search_messages → results.** Backend `$response['results']` (chat.php:1015).

SENDER_ID, RECEIVER_ID, GROUP_ID, CONTENT, SENT_AT, SENDER_NAME, SENDER_IMAGE`

**[OK] Request params / scope.** `scopeBody()` (chat.js:1354–1358) emits

## Diff 3 — Security

**[OK] CSRF.** All new actions are inside the single POST handler gated by
`csrf_verify()` (chat.php:11), before any `$_POST['action']` branch. New blocks
(885–1017) sit under it; none re-enter or bypass. No duplicate/removed gate.

**[OK] Group membership.** `pin_message`/`unpin_message`/`list_pins` call
`isGroupMember($pdo,$gid,$me)` before acting on a group scope (chat.php:898);
`set_typing` likewise (chat.php:991); poll's group typing is inside the existing
`isGroupMember` branch (chat.php:625,643). DM scope uses `dmConvKey($me,$peer)` —
keyed to the session user, so a user can only pin/type in a DM that includes them.

**[OK] Author-scoping (P2).** `edit_message`/`delete_message` pass session `$me`
(chat.php:954,972); repo enforces `SENDER_ID = ?` in SQL (MessageRepository:133,160).
Non-author → 0 rows → `success=false`. No posted user id trusted.

**[OK] No inline SQL for new features.** Every new data access goes through
`MessageRepository` prepared statements. chat.php's new blocks contain zero raw SQL
strings; the only SQL in the poll block is the pre-existing message/call fetches.

**[OK] Search wildcards escaped.** `searchMessages` escapes `\`, `%`, `_`
(MessageRepository:282) and binds with `ESCAPE '\\'` (:292). LIMIT bound
`PARAM_INT` (:305). Term passed raw from backend (chat.php:1015).

**[OK] Input validation.** `message_id > 0` enforced (chat.php:919,945,967);
`edit_message` requires non-empty trimmed content (:949); scope actions require
`group_id` or `receiver_id` (:893,986); search trims + short-circuits empty `q`
(:1008).

## Schema conflict re-confirmation (per task)

**[OK] IS_READ / GROUP_ID idempotently guard-added.** Both are added inside the
`feedora_msg_enh_migrate` stored proc behind `IF NOT EXISTS (… information_schema.COLUMNS …)`
checks: `GROUP_ID` (migration:63–69, + FK), `IS_READ` (migration:79–83),
`RECEIVER_ID` made nullable only `IF EXISTS … IS_NULLABLE='NO'` (migration:72–76).
Re-runnable, pre-8.0.29 safe. Proc is dropped before and after the CALL. The
01_schema §5 conflict (these cols absent from canonical `Feedora.sql`) is correctly
neutralized by this defensive migration — confirmed present and idempotent. The
backend additionally degrades soft (try/catch → false/[]) if the migration hasn't
been applied, so a pre-migration request fails with `success=false`, not fatally.

## WARNs (informational — not blockers)

**[WARN] Poll does not propagate peer edits/deletes to already-rendered messages.**
Boundary: frontend poll consumer ↔ backend poll payload. The unified `poll` returns
only *new* messages (`MESSAGE_ID > last_message_id`, chat.php:630,649); there is no
"mutations since id" channel. So if the **peer** edits/deletes a message already on
your screen, the change appears only on the next full `get_messages`/reload (those
rows carry `EDITED_AT`/`IS_DELETED` via `SELECT m.*` and `decorateMessage` renders
them). The actor's own edit/delete updates instantly (local DOM mutation).
**Judgment: ACCEPTABLE, not a blocker.** It is a known eventual-consistency limit,
honestly flagged in 03 §5, with a correct on-load reconciliation path. No contract
field is wrong — the rendered state converges. If the leader wants live peer-edit
propagation, that's a future enhancement (add a `mutations` array to the poll),
not a defect in this bundle.

**[WARN] CLAUDE.md ↔ repo Playwright contradiction.** `CLAUDE.md` forbids Playwright
("No Third-Party Test Tooling"), yet the repo ships a Playwright MCP plugin and the
prompt references a `tests/` suite. Per instruction I did **not** run Playwright and
relied on `npm run build` + `php -l` + source diffing. **Flagging once for the
leader to resolve the policy contradiction** — not a code defect.
